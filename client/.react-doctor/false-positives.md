# React Doctor - False Positives

## react-doctor/no-fetch-in-effect

- `src/components/mission/WaypointRouteList.jsx:191` - `fetch` va con `AbortController` + cleanup correcto (`controller.abort()` en el return del efecto). El proyecto no adoptó react-query/swr; este es exactamente el caso de excepción documentado por la propia regla ("one-shot fetch with proper AbortController cleanup in a small project that has not adopted a data-fetching library").
- `src/hooks/useMarkerTypes.js:9` - mismo patrón: `AbortController` + cleanup, más un cache a nivel de módulo (`cachedTypes`) que evita refetch en montajes posteriores.
- `src/scene3d/core/useMartinStatus.js:13` - usa un flag `cancelled` (no AbortController, pero equivalente: evita `setState` tras desmontar) dentro de un polling de `setInterval` con cleanup que limpia el interval y marca `cancelled = true`.
- `src/map/draw/MapGeofenceEdit.js:73,99,118` - el analizador ve un `fetch(...)` léxicamente dentro de un `useEffect`, pero en los tres casos el fetch vive dentro de un `listener` async que MapboxDraw invoca vía `map.on('draw.create'|'draw.delete'|'draw.update', listener)` - o sea, un callback de evento de una librería de terceros, no código que corre cuando el efecto se dispara. El efecto solo hace `map.on`/`map.off` (setup/cleanup del listener), el patrón textbook correcto para sincronizar con una librería imperativa.
- `src/map/geocoder/MapGeocoder.js:12` - mismo patrón: el `fetch` está dentro de `forwardGeocode`, un callback que `MaplibreGeocoder` invoca cuando el usuario escribe en la caja de búsqueda del mapa. El efecto solo registra/desregistra el control (`map.addControl`/`map.removeControl`).

## react-doctor/no-array-index-as-key

- `src/pages/LinearGauge.jsx:89` (`i` en `for (let i = start; i <= end; i += tickInterval)`) - `i` es un valor de tick matemático (representa una altitud/medida), no una posición de array; ya es único por construcción y la lista se reconstruye completa desde valores calculados en cada render, nunca se reordena/filtra un array existente.
- `src/components/mission/MissionElevation.jsx:213` (`elevProfile.map((_, index) => ...)`, `key={`sel${index}`}`) - `index` ES el identificador de negocio real (número de ruta), también usado como `value={index}` y como key de lookup (`elevProfile[selectRT]`) en el resto del componente.

### DIFERIDO (requiere decisión de arquitectura) - ver `client/CLAUDE.md` sección "Known Issues Needing Architectural Decisions"

- `src/components/mission/RouteRouteList.jsx:266` (`route.wp.map((waypoint, index_wp) => ...)`) - waypoints
- `src/components/planning/BaseList.jsx:135` - bases
- `src/components/planning/ElementList.jsx:115` - elements

Los tres comparten la misma causa raíz: el schema de datos (`{ pos: [...] }` para waypoints, `{ latitude, longitude, name, ... }` para bases/elements) no tiene campo `id`, pero los reducers SÍ hacen `splice()` en tiempo real (`missionActions.addWaypoint` con `insertAt`, `deleteWaypoint`, `DeleteElement`) - no es solo append/clear. El index como key puede reasignar estado/DOM de React a la fila equivocada al insertar/borrar en el medio de la lista. El fix correcto (agregar `id` estable con `crypto.randomUUID()` en el momento de creación, en los reducers de `store/mission.js`) requiere decidir la estrategia de migración para misiones ya guardadas (toca `MissionConvert.js` y posiblemente el parser de misión del servidor) - deliberadamente no se tocó en este pase.

## react-doctor/no-unknown-property

- Todo `src/scene3d/**/*.jsx` (65 casos en 9 archivos: `R3FCanvas.jsx`, `Drone.jsx`, `R3FDevices.jsx`, `MapTileGround.jsx`, `Arrow3D.jsx`, `NumberedSphere.jsx`, `MapVectorGround.jsx`, `Polyhedron.jsx`, `R3DMarkers.jsx`) - elementos JSX en minúscula como `<mesh>`, `<group>`, `<meshStandardMaterial>`, `<perspectiveCamera>`, `<primitive>` son el reconciler custom de React Three Fiber (renderiza a objetos Three.js, no al DOM), no elementos HTML. Props como `position`, `rotation`, `args`, `attach`, `intensity`, `map`, `roughness`, `metalness`, `depthTest`/`depthWrite`, `sunPosition`, `rayleigh`, `turbidity` son válidas en R3F y no tienen equivalente HTML. Verificado archivo por archivo: no hay ningún elemento HTML real ni typo genuino (class/for/tabindex) mezclado en estos 9 archivos - son 100% código de escena 3D.

## react-doctor/no-json-parse-stringify-clone

- `src/store/mission.js:217` (`copyWaypoint` reducer) - `state.route[routeIndex].wp[wpIndex]` dentro de un reducer de Redux Toolkit (`createSlice`) es un draft/Proxy de Immer, no un objeto plano. Verificado con un test real: `structuredClone()` sobre un draft de Immer lanza `DOMException: could not be cloned` porque el algoritmo de clonado estructurado no puede serializar el Proxy. `JSON.parse(JSON.stringify(x))` funciona acá porque pasa por texto plano y escapa el proxy; `structuredClone` no tiene ese efecto secundario y por eso falla. No convertir sin antes envolver en algo que materialice el draft a un objeto plano primero (ej. `current(state.route[...])` de Immer).

## react-doctor/no-derived-state + no-derived-state-effect (alias visto también como `no-adjust-state-on-prop-change`, error severity, mismo caso)

- `src/components/mission/WaypointRouteList.jsx:63,66` (`ActionValueField`) y `:113,116` (`WaypointParamField`) `draft`, y `:214` (componente principal) `posInput` - patrón deliberado de "buffer local editable con commit on blur": el usuario escribe en el input (`onChange` actualiza el buffer sin tocar el valor real todavía) y solo `onBlur`/`onCommit` sube el cambio. El `useEffect` que resincroniza el buffer existe para reflejar cambios EXTERNOS al valor mientras el campo no está siendo editado activamente (otro proceso actualiza el waypoint, o arrastrar el marcador en el mapa mientras el acordeón de edición está abierto - ver comentario en línea 211: "Keep posInput in sync when waypoint is updated externally"). Eliminar el state y computar inline rompería la posibilidad de escribir un valor intermedio/inválido temporalmente (ej. borrar el campo para reescribir) sin que se pise letra a letra por el valor externo. No es un simple espejo de prop - es el patrón estándar de input controlado con commit diferido.
- `src/pages/Scene3DEditorPage.jsx:126` (`XYZEditor`) `local` y `:192` (`HeadingEditor`) `local` - mismo patrón de buffer editable con commit on blur/Enter (comentario explícito en línea 128: "keep local in sync when parent changes (e.g. tab switch)"). Igual que en `WaypointRouteList.jsx`: eliminar el state rompería la edición de coordenadas/heading letra a letra.
- `src/components/mission/RoutesList.jsx:22` `expanded` (via `useEffect([selectwp])`) - `expanded` tiene dos dueños legítimos: (1) el usuario clickeando un acordeón manualmente (`setExpanded` pasado como prop a `RouteRoutesList`, que lo llama en su propio `onChange`), y (2) una selección externa de waypoint hecha clickeando el mapa (`dispatch(missionActions.selectpoint(...))` en `MapMissionsCreate.js:127`, que SIEMPRE debe ganar y forzar la apertura del acordeón correspondiente - confirmado con el usuario, ambos gestos son mutuamente excluyentes en la práctica, nunca simultáneos). Además, `selectpoint` reemplaza el objeto completo en el store en cada dispatch (`state.selectpoint = action.payload`), así que el mismo waypoint clickeado dos veces sigue dando un objeto nuevo - el efecto reacciona a un EVENTO discreto (un click en el mapa), no a un cambio continuo de valor; computar `expanded` inline desde `selectwp` haría que el usuario nunca pudiera cerrar el acordeón manualmente, porque se recalcularía siempre igual en cada render. La forma de efecto reaccionando a evento es la correcta acá, no el anti-patrón que la regla busca. Este mismo efecto también aparece bajo `no-prop-callback-in-effect` por el `setScrool(...)` de la línea 23 (prop-callback del padre para hacer scroll hasta el waypoint) - mismo análisis: ambas llamadas (`setExpanded` y `setScrool`) reaccionan al mismo evento discreto de click en el mapa, no hay handler local al que moverlas.

## react-doctor/no-event-handler

- `src/components/chat/useChatLogic.js:78` `if (open) fetchAvailableChats()` - `open` es una prop que controla la visibilidad del `ChatDrawer`, pero el click que la cambia (`setChatOpen(true)`) vive en `MainPage.jsx`, varios componentes por encima, pasado hacia abajo como callback (`setChatOpen` prop-drilled a otro componente que renderiza el botón real). No hay ningún handler local dentro de `useChatLogic`/`ChatDrawer` al que mover el fetch - el efecto reaccionando a `open` es la única forma de conectar "el drawer se hizo visible" con "buscar chats disponibles" sin acoplar el botón lejano a la lógica de datos del chat.
- `src/components/mission/RouteRouteList.jsx:153` `if (matchedCategory && route.uav_type !== matchedCategory) { dispatch(...) }` - hay un handler local real (`handleRouteFieldChange('uav', ...)` en el `TextField` de UAV id, línea 247) pero `matchedCategory` no depende solo de ese click: se deriva de `devices` (`useSelector((state) => state.devices.items)`), que se actualiza vía WebSocket de forma completamente asíncrona e independiente (`SocketController.jsx` despacha `devicesActions.update`/`refresh` en mensajes entrantes). El efecto necesita reaccionar tanto al click local (usuario asigna un `uav` que ya matchea un dispositivo existente) como al evento externo (el dispositivo con ese nombre se conecta/cambia de categoría DESPUÉS de que el usuario ya asignó el nombre). Mover solo al handler de click perdería el segundo caso.
- `src/map/draw/MapGeofenceEdit.js:153` `if (selectedGeofenceId) { map.fitBounds(...) }` - `selectedGeofenceId` es una prop; el click que la cambia (`setSelectedGeofenceId`) vive en `GeofencesPage.jsx` y se pasa a un componente HERMANO distinto (`<GeofencesList onGeofenceSelected={setSelectedGeofenceId}>`), no a `MapGeofenceEdit` mismo. No hay forma de interceptar ese click desde este componente - el efecto reaccionando a la prop es la única conexión posible entre "se seleccionó un geofence en la lista" y "centrar el mapa en él".
- `src/scene3d/scene/R3DMarkers.jsx:12` (marcado en la línea de `useModelLoader(item.type)`, pero el patrón real está en `useEffect(() => { if (clone) invalidate(); }, [clone, invalidate])` más abajo) - `clone` no viene de un click de usuario, viene de `useModelLoader` (fetch async de un modelo GLTF) vía `useMemo`. El comentario explícito lo confirma: "Tell R3F to draw a frame when the model finishes loading". No hay handler de UI al que mover esto - es notificación de que una carga asíncrona terminó, no un evento de interacción.
- `src/scene3d/scene/R3FDevices.jsx:48` `const loc = position.find(...)` dentro de un `useEffect` que actualiza posición/rotación 3D del dron - `position` es telemetría en tiempo real (posiciones de todos los dispositivos vía Redux, actualizada por WebSocket), no el resultado de un click de usuario. El efecto sincroniza el estado imperativo de Three.js (refs de posición/rotación) cada vez que llega un nuevo dato de telemetría - no hay ningún handler de UI al que mover esto.
- `src/shared/components/SelectField.jsx:34-45` (dos bloques dentro del mismo `useEffect`: `getItems(items[value])` y el auto-select `onChange({target: {value: items[0]}})`) - `value` viene controlado externamente por el padre (ej. `sendTask.objetivo.id` de Redux en `PlanningPage.jsx`, pasado a través de `PlanningTab.jsx`), y `items` se llena de forma asíncrona por `endpoint` (fetch). El efecto necesita notificar/auto-seleccionar cuando el fetch TERMINA mientras `value` ya venía seteado desde afuera - no hay ningún click de usuario en ese momento al que mover la lógica; es sincronización entre una prop controlada externamente y datos que llegan async.

## react-doctor/no-effect-event-handler

- `src/components/mission/WaypointRouteList.jsx:191` `if (!isOpen || !uavType) return; fetch(...)` - `isOpen` sí viene de un click (expandir el acordeón, handler `handleChange_wp` en el mismo archivo), pero el fetch también depende de `uavType`, una PROP que cambia desde un componente padre distinto (`RouteRouteList.jsx`, el selector de tipo de UAV de la ruta) - completamente fuera del handler del acordeón. Si el usuario cambia el tipo de UAV mientras el acordeón del waypoint ya está abierto, el catálogo de acciones debe refrescarse igual. ## react-doctor/jsx-no-jsx-as-prop

- `src/components/mission/MissionTrackingPanel.jsx:19,24` `primary={<Typography>...` / `secondary={<Typography>...` dentro de `MissionTrackingRow` - MUI's `ListItemText` solo acepta `ReactNode` en `primary`/`secondary`, no soporta un render-prop ni un tipo de componente, así que construir el elemento inline es inevitable con esa API. La fila completa (antes generada inline dentro del `.map()` del panel) ya se extrajo a `MissionTrackingRow` envuelto en `React.memo` (mismo patrón que `RouteTrackingRow`), y `handleSelect` se estabilizó con `useCallback` - así que ese trabajo de reconstrucción del JSX solo ocurre cuando cambian los datos de ESA fila puntual, no en cada tick de telemetría que toca a las demás misiones de la lista. El análisis estático solo ve "JSX inline pasado como prop" y no puede detectar que el componente contenedor ya está memoizado - el costo real que la regla busca evitar (re-render de toda la lista) ya está resuelto.

## react-doctor/no-prop-callback-in-effect (RESUELTO sin Context Provider)

- `src/components/devices/useFilter.js` (antes duplicado también en `src/shared/useFilter.js`) - la receta canónica sugiere mover el estado compartido a un Context Provider para eliminar el efecto, pero eso hubiera sido una migración de arquitectura real (toca 4 páginas: `MainPage.jsx`, `MainPage3D.jsx`, `DevicePage.jsx`, `DevicePage3D.jsx`). Se optó por una alternativa más chica que resuelve la misma causa raíz: el hook dejó de recibir `setFilteredDevices`/`setFilteredPositions` como props-setter y en su lugar calcula ambos valores con `useMemo` y los devuelve directamente (`const { filteredDevices, filteredPositions } = useFilter(...)`). Ya no hay ningún `useEffect` empujando estado derivado hacia el padre - el antipatrón que la regla busca desapareció sin tocar Context. De paso se eliminó la duplicación entre `shared/useFilter.js` y `components/devices/useFilter.js` (eran archivos byte-idénticos) y se limpiaron los 2 call-sites (`DevicePage.jsx`/`DevicePage3D.jsx`) que descartaban el resultado con `void filteredDevices` - en `DevicePage3D.jsx` ni siquiera se usaba `filteredPositions`, así que se eliminó la llamada al hook por completo ahí. Verificado con `npx vite build` y `react-doctor --scope changed` reales: el finding no vuelve a aparecer.
